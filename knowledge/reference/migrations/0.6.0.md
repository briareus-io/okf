# Migrating to OKF CLI 0.6.0

CLI and plugin 0.6 require a shared context protocol: the plugin accepts stable CLI versions
`>=0.6.0, <0.7.0`. The manifest schema has its own version and does not change on every CLI release.
Core OKF document conformance remains distinct from the bundle tooling profile.

## Move configuration deliberately

The portable layout uses root `okf-bundle.yaml` for settings, guidance, and workflows, root
`.okf-bundle/` for support files, and workspace `okf-catalog.yaml` for IDs, locations, and default
selection. Ontology remains separate. Legacy TOML remains readable during compatibility.

Run doctor to inspect legacy configuration and request an explicit migration plan when ready.

```text
okf doctor --migrate-config okf.toml --migration-plan /tmp/config-migration.yaml
okf doctor --migration-apply /tmp/config-migration.yaml
```

For a path-only legacy default, supply `--default-bundle-id <id>` when the plan needs a new
registration identity. Review affected bundles, destination files, rebased ontology paths, conflicts, and any registration
ID that must be supplied. Apply the reviewed plan rather than moving keys mechanically. Present
but invalid manifests must be repaired; they do not authorize falling back to legacy settings.

Keep source snapshots and unrelated legacy content intact. Remove `okf.toml` only when all required
values have migrated and no remaining data depends on it. Equal duplicate definitions can be
reported as redundant; conflicting values require a decision. Do not convert an external ontology
into a copied local file merely to make a path portable.

## Update automation

Read `okf schema` and each command's supported options. JSON may include distinct guidance records;
continue validating the actual process exit and operation-completion record. Do not parse guidance
as concept content. Consumers must explicitly support new record kinds or select an appropriate
incidental presentation mode.

Agent workflows load full context before acting and cache by effective context digest, including
instruction files. `--all` and historical context are inspection, not procedure activation. Missing
required instruction files are actionable errors. Shared scripts and templates are not automatic
CLI hooks.

Core validation includes Markdown under its original file boundary. Bundle-profile validation
excludes `.okf-bundle/` support Markdown. Report which profile passed; older readers may treat those
files as malformed concepts. Knowledge-only exports omit support workflows and are not equivalent
portable bundles.

## Opt into remote dependency management

Existing directory registrations remain available. Git registrations introduce accepted lock state
and managed read-only content. Plan and review the initial candidate before applying it, then sync
exact accepted content. Ordinary retrieval does not auto-fetch. Location overrides must preserve
accepted bytes and access policy.

Logical `okf://<bundle-id>/<path>` references are optional. Existing paths keep their meaning and
are not automatically rewritten. Ordinary Markdown readers may need exported links. A logical link
follows the lock; source-specific snapshot expectations remain independent evidence requirements.

and [remote dependencies](../../guides/remote-dependencies.md) for the supported workflow.
