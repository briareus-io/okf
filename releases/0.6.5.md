# OKF CLI and plugin 0.6.5

OKF 0.6.5 adds explicit cross-bundle examination to ontology-gated changesets. A Planning
Increment can now reference a Product Specification in a registered sibling bundle, have its
actual type checked, and publish through the guarded changeset mechanism. The additional
bundles are read dependencies; all changes still belong to one selected bundle.

## Upgrade and compatibility

- Install CLI and plugin 0.6.5 together. The plugin now requires a stable CLI version
  `>=0.6.5, <0.7.0`, because its generated references describe the new scoped changeset
  options and evidence. The preflight rejects older CLIs instead of advertising unsupported
  commands. The workspace and both plugin manifests are 0.6.5.
- The OKF document format remains v0.2. Manifest v1, catalog v2, and lock v1 are unchanged.
  Existing unscoped changeset invocations and successful unscoped JSON payloads retain their
  interface. The scope options and optional JSON scope evidence are additive.
- **Gate correctness tightening:** an ontology-checked `okf://` reference without explicit
  examination scope now fails with `write-gate-incomplete`. Previously, the gate could treat
  it as an external URL and skip the typed check. Add explicit scope and preview again;
  do not disable a required gate to preserve the old unchecked behavior.
- Upgrades from earlier 0.6 releases should also review their intervening release notes.
  The [0.6 migration guide](../knowledge/reference/migrations/0.6.0.md) describes the existing
  configuration and automation migration from older minor versions.

## Scoped ontology-gated changesets

`changeset plan`, `changeset apply`, and `changeset digest` accept repeatable
`--scope-bundle ID` or deliberate `--catalog-scope`. The selected bundle and each requested
target must be registered and available for examination. Catalog registration alone does
not broaden the gate's scope. `changeset recover` remains unscoped.

For a catalog registering `planning.main` and `product.main`, an ontology reference rule can
use `target: product.main:Specification`, while an Increment's field contains
`../product/spec.md` or `okf://product.main/spec.md`. Preview and apply with the same read scope:

```sh
okf changeset plan --bundle-id planning.main --from @plan.yaml \
  --require-ontology-gate --scope-bundle product.main --json

# Substitute the base_digest from the reviewed plan.
okf changeset apply --bundle-id planning.main --from @plan.yaml \
  --require-ontology-gate --scope-bundle product.main --expect REVIEWED_BASE_DIGEST
```

To obtain a baseline independently, use the same scope:

```sh
okf changeset digest --bundle-id planning.main --scope-bundle product.main --json
```

The feature also applies when bundle policy enables the gate without
`--require-ontology-gate`. Neither scope option authorizes operations in the target bundle.

### Target interpretation and failures

- `product.main:Specification` means the registered owner must be `product.main` and the
  target concept must have type `Specification` or a subtype established by that target
  bundle's ontology. The bundle root is not a typed concept.
- Unqualified target types also use the actual target bundle's ontology for inheritance.
  An exact type match does not require a target ontology; checking a possible subtype does.
  The `bundle-id:Type` form is reserved for qualification in scoped gate matching. Unscoped
  matching retains literal type-string behavior.
- The scoped check handles ordinary relative paths, logical OKF references, reference target
  unions, and relationship-kind target narrowing. It retains the policy that unchanged
  violations may remain, while new or worsened findings reject publication.
- An unexamined or unavailable target bundle produces `write-gate-incomplete`. A missing
  concept in an examined bundle, an incorrect bundle identity, or an incompatible target
  type is an ontology finding. Existing changeset dangling-reference validation may reject a
  missing concept before the ontology gate runs.
- Artifact paths cannot alias a different Markdown concept for type checking. Logical
  references remove only their final `.md` suffix, preserving concept names that themselves
  end in `.md`.

## Baseline, publication, and JSON evidence

The scoped baseline binds the primary bundle, whole examined target-bundle file snapshots,
effective settings and ontology identity/content digests, catalog bytes and resolved
registrations, workspace configuration, and requested scope. A change to an unrelated file
in an examined target bundle can therefore invalidate a reviewed digest. Use the same scope
for plan, digest, and apply; obtain and review a new plan after a conflict.

Apply checks the baseline again and holds target-bundle reader guards through the selected
bundle's journaled publication. Cooperating OKF target writers cannot publish while those
guards are held. A changed or unavailable scoped dependency when applying a retained plan
produces `baseline-conflict`. A fresh command unable to examine the requested scope can fail
with `write-gate-incomplete` before it obtains a comparable baseline.

Successful scoped `baseline` and `changeset-summary` JSON records include optional
`scope` evidence with `requested`, `examined`, and `unavailable` arrays. Identities come from
the guarded capture and include the primary bundle. Successful examination requires every
requested bundle, so `unavailable` is empty. Unscoped records omit this optional object.
`okf schema --json` and the generated command and skill references describe the new fields.

Catalog mappings are recaptured and checked before publication, but catalog edits and
arbitrary filesystem editors are outside the bundle-lock protocol. The operation does not
provide an atomic snapshot of all catalog/filesystem activity or a multi-bundle write
transaction. Existing journaled, per-file publication guarantees remain in effect. Scoped
concept changesets do not extend ontology sidecar updates' reference examination scope.

## Validation and distribution

Regression coverage includes successful gated plan/apply, policy-enabled gates, explicit and
catalog-wide scope, target identity/type/inheritance checks, unavailable and missing targets,
relationship narrowing, baseline conflicts, target writer exclusion, single-bundle write
ownership, JSON evidence, and the path/logical-reference gate corrections.

Release assets are built by the release workflow for macOS and Linux on ARM64 and x86_64,
with `SHA256SUMS` and the standalone installer. Official binaries include `url-sources`.
macOS artifacts follow the established signing and notarization workflow. Local release
preparation alone does not publish these assets.
